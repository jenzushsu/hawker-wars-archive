# P5-C rules worker and verified recovery

This increment connects one rules-only exhibition round to the fenced Postgres store. It advances a bounded tick from authoritative recovery, persists the result atomically and stops on errors. It does not dispatch providers, accept votes or connect the browser to live data. Only the `rules` policy and a clean schedule are supported; recovery explicitly records voting as disabled.

## Recovery and failure behavior

The worker validates round identity, classification, policy list, contract/configuration versions, stored schedule identity, tick/sequence and simulator state. Recovery is checked against deterministic rules replay through the committed boundary, rather than trusting a matching self-reported checksum. The next tick is derived only after validation. A distinct private worker version prevents interpreting the older generic recovery-envelope examples as runnable simulator state.

Lease ownership and expiry remain database-authoritative. The worker re-reads private recovery under its current fence, computes one next tick and commits with a deterministic idempotency key. It does not retry a failed or uncertain commit within the invocation. A later invocation reads the durable state before advancing; it does not assume the previous request failed just because its acknowledgement was lost. Lease release is best-effort; expiry remains the fallback after a process crash.

Database readiness gates this worker to at least five seconds between ticks, including across process restarts. The pacing timestamp is operational state outside the simulator checksum. A transaction that fails rolls back both the tick and its pacing update. An immediate repeat invocation returns `waiting`; a race that loses readiness or fencing is rejected by the database. Completed rounds return `completed` without restarting a lease or adding a closing decision.

## Running against configured staging infrastructure

Apply both checked-in P5 migrations first. Set `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` only in the trusted worker environment. The repository does not load `.env.example` automatically, and the frontend requires neither secret.

```sh
# Create a private rules-only round and commit at most one tick.
pnpm worker:rules --round YOUR_ROUND_UUID --create --seed 7

# Resume from the persisted boundary; do not repeat --create.
pnpm worker:rules --round YOUR_ROUND_UUID

# Run at most 121 bounded steps, waiting at least five seconds between steps.
pnpm worker:rules --round YOUR_ROUND_UUID --steps 121
```

Use a UUID generated by your operator tooling. The CLI restricts seed selection to development seeds 0–99. `--publish` is allowed only with `--create` and exposes sanitized public records; it does not activate a live viewer. Each process has a fresh owner UUID unless `--owner` is supplied. Do not run the worker inside a spectator page request or rely on an unawaited Vercel background task.

A lost create acknowledgement requires checking the round before deciding whether to create again. The worker stops rather than guessing through an error. Stop the process to stop future ticks; durable operator pause/cancel/kill-switch APIs and a supervised production scheduler remain separate work. A stale lease can delay takeover until its expiry.
